1. The one breaking change

Breaking DELETE /api/v1/admin/users/{user_id} now returns 200 with a JSON body. It previously returned 204 No Content.

Any client that branches on status === 204 after deleting a user needs updating. The behaviour is unchanged by default — it still soft-deletes — only the response gained a body:

{
  "user_id": 1786194521387,
  "email": "aisha.khan@h7ed.com",
  "full_name": "Aisha Khan",
  "mode": "SOFT",
  "firebase_auth_deleted": false,
  "deleted_records": {},
  "detail": "User deactivated. History is preserved and the Firebase account is disabled."
}

Everything else in this document is additive. Existing requests and response fields are unchanged, so nothing else needs touching before you're ready.

2. User profile fields

New POST /api/v1/admin/users and PUT /api/v1/admin/users/{user_id} accept the fields below, and every response carrying a user object returns them.

All of them are optional. The old minimal payload {"full_name": "...", "role": "STUDENT"} still works unchanged. Nothing is enforced per role — the backend does not reject a guardian contact on a teacher — so the form decides which sections to show based on role.

UserOut also gained updated_at (nullable ISO datetime), set on every profile edit.

Update semantics — worth reading before building the edit form

Omitted and null both mean "leave unchanged". There is no way to clear a field back to empty by sending null.

This is deliberate: a form that sends every input on submit, defaulting untouched ones to null, would otherwise wipe data the person editing never saw. To blank a field, send an empty string — it is stored as null.

Validation to mirror in the form:

  • Phone, admission number, roll number and employee ID are trimmed; whitespace-only becomes null, so two blank admission numbers don't collide.
  • admission_number and employee_id return 400 when already held by someone else. The detail names who: "The admission number 'ADM-2026-014' is already assigned to Sara Ahmed (id 1786…)." Surface it directly.
  • Changing email to one already in use returns 400.

New Role changes via PUT

PUT /api/v1/admin/users/{user_id} now accepts role.

Changing a role signs that user out. The backend re-issues their Firebase custom claims and revokes their existing tokens, because claims drive what the frontend renders and a stale token would leave them on the wrong navigation until it expired.

The affected user's next request returns 401 and they must sign in again. Warn the admin in a confirmation step before submitting a role change.

3. User deletion

DELETE /api/v1/admin/users/{user_id} now has two modes. Response is 200 with the UserDeleted body shown in section 1.

QueryDefaultEffect
permanentfalsefalse deactivates and disables the Firebase login (reversible). true erases the profile and the Firebase Auth account.
forcefalseOnly read when permanent=true. Also deletes every record referencing the user.

Soft delete — unchanged behaviour

DELETE /admin/users/{id} → 200, mode: "SOFT". History keeps resolving to a name. Reverse with POST /admin/users/{id}/reactivate.

Permanent delete — two-step confirm

DELETE /admin/users/{id}?permanent=true returns 409 while anything still references the user, with a detail listing what:

Cannot permanently delete this user because they are still referenced by:
2 student enrollment(s), 14 attendance record(s) as student, 3 exam grade(s) as student.
Retry with &force=true to delete those records too, or use the default soft delete
to keep the history.

The intended flow is: call without force, show the admin exactly what would be destroyed, then repeat with &force=true on confirmation. The success response reports what actually went:

{
  "user_id": 1786194521387,
  "mode": "PERMANENT",
  "firebase_auth_deleted": true,
  "deleted_records": { "student enrollment(s)": 2, "exam grade(s) as student": 3 },
  "detail": "User aisha.khan@h7ed.com permanently deleted. 5 referencing record(s) were removed."
}

Watch firebase_auth_deleted: if it is false the login may still exist and detail says so — show that, it needs manual cleanup in the Firebase console.

Guards you should reflect in the UI

  • 400 — an admin cannot permanently delete the account they are signed in with. Hide or disable the option on their own row.
  • 409 — the last active admin cannot be removed by either mode.

4. Timetable

New A timetable entry is a recurring weekly rule, not one row per calendar day: "Grade 7A does Maths with Mr Rahman on Tuesdays, 09:00–09:45, Room 12, from 1 Sep to 20 Dec". A term's schedule is a few dozen rows.

Time and date formats

Send "09:00", receive "09:00:00". Input accepts either form; output is always HH:MM:SS. Normalise on the way in if you round-trip an entry through an edit form.

Times are local school wall-clock, with no offset — a period is at 09:00 regardless of DST. Do not convert them to UTC. The school zone is server-side (SCHOOL_TIMEZONE, currently Asia/Dubai) and is reported by GET /admin/reminders/status.

Clash handling — 409

Creating or editing a period is refused when it double-books the class or the teacher. Rooms are deliberately not checked. The detail names the offending entries:

This period clashes with the existing timetable: the class already has Physics on
Monday 09:00-10:00 (entry 1786194600002). Fix the clash, or resend with
?allow_conflicts=true to schedule it anyway.

Pass ?allow_conflicts=true on POST or PUT to override. Suggested UX: show the clash, offer "Schedule anyway" as the secondary action.

Two things that intentionally do not clash: back-to-back periods (09:00–10:00 and 10:00–11:00 touch but don't overlap), and editing an entry into a slot it already partly occupies.

Bulk upload

POST /api/v1/admin/timetable/bulk
{
  "replace_existing": true,   // wipe the current timetable for every class_id in `entries`
  "entries": [ { …TimetableEntryCreate… }, … ]   // 1–500
}

Rows that fail are reported rather than failing the request — one bad row does not cost you the other thirty-nine:

{
  "created": [ …TimetableEntryOut… ],
  "replaced": 12,
  "skipped": [ { "index": 7, "reason": "This period clashes with … (entry 178…)" } ],
  "detail": "24 period(s) created, 12 replaced, 1 skipped."
}

replace_existing: true makes re-uploading a corrected schedule idempotent instead of doubling it up. skipped[].index is the position in the array you sent, so you can highlight the offending row in the upload preview.

Both roles: /timetable takes an optional day_of_week; /timetable/day takes on_date (defaults to today in the school zone); /timetable/upcoming takes days_ahead (0–31, default 7) and limit (1–50, default 10). Students see every class they are enrolled in.

ScheduledPeriod — the recurring rule resolved against a real date

This is what the "today" and "what's next" views should render. The backend has already done the weekday and timezone arithmetic:

{
  "entry": { …TimetableEntryOut… },
  "on_date": "2026-08-10",
  "starts_at": "2026-08-10T09:00:00+04:00",   // ISO 8601, school UTC offset
  "ends_at":   "2026-08-10T09:45:00+04:00",
  "starts_in_minutes": 15,                     // negative once the period has begun
  "is_current": false                          // true while it is happening
}
  • is_current → highlight the period in progress.
  • starts_in_minutes → "next class in 15 minutes". Goes negative, so use > 0 for a countdown.
  • upcoming looks forward across days, so a subject that only meets on Thursdays still appears when asked on a Friday.

5. Class reminders

New The backend emails students (and teachers) before a timetabled period starts. This runs on a server-side schedule — there is nothing for the frontend to trigger or poll for reminders to work.

What the frontend does own:

  • reminder_opt_in on the user profile — a toggle on the profile form. Defaults to true. Only an explicit false suppresses reminders.
  • Admin monitoring screens, if you want them:
MethodPathPurpose
GET/api/v1/admin/reminders/statusIs the scheduler running, offsets, last sweep, and server_time_local
GET/api/v1/admin/reminders/previewWhat the next sweep would send. Sends nothing — safe to call repeatedly
POST/api/v1/admin/reminders/run202 + {job_id, poll_url} — poll GET /admin/jobs/{job_id}
GET/api/v1/admin/reminders/logReminders actually delivered, newest first. ?limit= (1–500), ?user_id=

Both status and preview include mail_configured. When it is false, SMTP is not set up and no reminder can be delivered — surface that on the admin screen rather than showing a healthy-looking empty log.

Running a sweep by hand cannot double-email anyone; already-sent reminders are skipped server-side.

6. Drive & Meet changes from the previous update

These shipped just before the timetable work and are also frontend-visible.

Changed Meetings now explain a missing link

LiveMeetingOut gained two fields, on both the teacher and admin endpoints:

  • meet_status — "CREATED" · "FAILED" · "MANUAL" (a link was typed in) · "SKIPPED" (generation not requested)
  • meet_error — why generation failed, when it did

A meeting is still saved with 201 when Meet generation fails, so check meet_status rather than assuming meeting_link is populated. On FAILED, show meet_error and offer the admin retry: POST /api/v1/admin/meetings/{id}/regenerate-link.

Changed Uploads report where the file actually landed

StudyMaterialOut gained storage_warning alongside the existing storage_provider. POST /api/v1/storage/upload gained requested_provider and warning.

If storage_provider is "LOCAL" while Drive or Cloud Storage was configured, the cloud upload failed and the file is on the API server instead — storage_warning says why. Show it as a warning on an otherwise successful upload.

New Admin can manage materials and meetings

Admins were previously limited to their own records, because the teacher endpoints filter by the signed-in user. These are system-wide:

  • GET /api/v1/storage/status — the storage half, available to teachers.
