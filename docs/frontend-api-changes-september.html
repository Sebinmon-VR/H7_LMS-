1. What to change in existing screens

Nothing was removed and no response shape changed in the September modules, so nothing breaks on deploy. Three things do need attention in screens you already have.

22 September update — the billing rework does remove things. The tuition /fee-plans endpoints are gone, replaced by packages; fee_plan_id has left the enrollment shapes; and the tuition fee breakdown now has one package line instead of one line per subject. See section 17 before touching the fee screens.

Changed UserRole has a fifth value

PARENT joins ADMIN, CLASS_TEACHER, TEACHER and STUDENT. Any exhaustive switch on role — a role picker, a navigation guard, a badge colour map — needs a branch for it, or parents land on whatever your default case does.

A parent's home is GET /api/v1/parent/children, which returns the children they may open together with per-child permission flags. Render the switcher from that, and hide a tab rather than letting the request 403.

Changed New fields on every user profile

Additive, all optional, on UserCreate, UserUpdate and UserOut. Existing forms keep working; the admission form should gain them.

FieldTypeNotes
academic_year_idintDefaults to the current year when a student is created
admission_category_idintCarries any standing fee concession
syllabusstringCBSE, ICSE, IGCSE — free text, drives library filtering
academic_streamstringScience, Commerce, Humanities
mediumstringLanguage of instruction

Changed POST /admin/users now fills in two fields

When the school's identifier mode is AUTO (the default), leaving admission_number or employee_id blank gets one issued — ADM-2026-0001, EMP-2026-0001. A value you send is always kept, so a migration carrying historical numbers is unaffected. Students also get academic_year_id set to the current year when you omit it.

The response carries whatever was assigned, so read it back rather than assuming the field is still empty. Switch to MANUAL under PUT /admin/finance/settings… see settings.

The payment page renders FeeBreakdownOut

/fees/me, /parent/fees/children/{id} and the admin preview all return the same shape, from the same computation. The totals relate as:

subtotal
  − discount_total
  + tax_total
  + convenience_total
  ± rounding_adjustment
  = total_amount

charge_total is the part of subtotal that is not teaching fees, so you can render "Fees" and "Charges" as sections without recomputing anything. Every line in line_items carries its own discount_amount, tax_amount and net_amount.

discounts_not_applied is worth surfacing on the admin screen. Each entry says why a rule did not fire — "household has 1 child; rule needs 2" — which answers the support question before it is asked.

Discounts

The two the brief asked for: basis: SIBLING with applies_from_nth: 2 gives the second child onward a concession while the eldest pays full fee, counted over the recorded household. basis: MULTI_REGISTRATION counts concurrent enrollments across both products — the "2 registrations at once" case.

is_stackable is off by default: rules compete and only the best-valued one applies. Make that visible in the rule editor, because a staff ward who is also a second child getting one concession rather than two will otherwise look like a bug.

New Payment gateway — recorded, not wired

No provider is integrated. POST /admin/finance/invoices/{id}/intents validates the amount, mints an idempotency key and records the attempt, but returns checkout_url: null and status: "CREATED".

Read gateway_enabled from the breakdown or the settings to decide whether to render "Pay online" at all. Until a provider is chosen, show fees, charges and tax and take payment offline through /payments.

7. Live classes — the join button

MethodPathPurpose
GET/classes/{meeting_id}/timingThe class clock. Poll for a countdown
POST/classes/{meeting_id}/joinReturns the link only if you may join
POST/classes/{meeting_id}/startTeacher opens the class
POST/classes/{meeting_id}/endCloses it
GET/classes/liveDashboard "join now" strip

Bind the join button to may_join and nothing else. It already accounts for the early-join window, the grace period, the status and whether the teacher has started. Anything you derive yourself will eventually disagree with the server, which enforces the same rule on /join and returns 409.

When it is false, show join_blocked_reason verbatim — it distinguishes "The class opens at 09:55", "Waiting for the teacher to start the class" and "This class has ended", which flags alone cannot.

Timings are computed server-side so a teacher's screen and a student's screen cannot disagree. Useful fields: starts_in_minutes, minutes_remaining, class_has_started, waiting_for_teacher, is_live, join_opens_at.

With auto_start_class on, a class opens on its timetabled time with no teacher action. With it off — the default — students see waiting_for_teacher: true until the teacher calls /start. A student in that state is waiting, not late; word the UI accordingly.

9. Calendar and tile view

GET /calendar?from_date=&to_date=&kinds=&group_by_day= — one endpoint for both views.

Every source is flattened to one event shape, so a week renders without knowing which collection a row came from. kind is TIMETABLE, LIVE_CLASS, TUITION_CLASS, EXAM or HOMEWORK — switch on it for colour and icon only.

  • group_by_day=true adds days[] with every date in the range including empty ones, so a month grid lines up without you synthesising blanks.
  • Homework has all_day: true and a due_date rather than a time — render it in the day header.
  • meeting_link is present only when the viewer may join right now. The calendar cannot be used to enter a room early.
  • Role decides the sources. A parent gets the union of their children's events, each tagged with student_id and student_name.
  • Ranges are capped at 90 days; longer returns 400.

14. Library — read-only mode and syllabus

Changed Two settings now gate the tuition library for students, independently:

  • student_library_uploads_enabled: false — upload endpoints return 403 for students. Hide the upload control.
  • student_library_downloads_enabled: false — POST /tuition/library/{id}/download returns 403 for students. They can still view in the browser.

Library items gained a syllabus array (["CBSE"]). When library_syllabus_filter is on, students see only items matching the syllabus on their profile — plus every untagged item, so turning the filter on does not blank an existing library. Teachers and admins always see everything.

17. Billing rework — terms, packages and family auto-mapping

Changed Three things changed together on 22 September: the academic year now carries two terms, tuition fees are packages rather than per-subject rates, and sibling households build themselves from guardian details. All existing billing data was cleared when this shipped, so every fee screen starts from empty.

The year is April to March, in two terms

Every AcademicYearOut (school and tuition) now carries terms[] — two entries with key (TERM_1 / TERM_2), name, start_date, end_date and is_current — plus current_term, the key today falls in. Years created before this carry the derived default: Term 1 from the year's start to 31 October, Term 2 from 1 November to the year's end.

FieldOnChange
start_date, end_datePOST …/yearsNow optional. Omit both and a name like "2026-27" resolves to 1 April 2026 – 31 March 2027
terms[]POST, PUT …/yearsOptional override: [{key, name?, start_date, end_date}], both terms, inside the year. Omit for the April–October / November–March split. Changing the year's dates without terms re-derives them
instalments[]school FeeBreakdownOut, FeeInvoiceOutWith no instalment plan, a school fee now splits into two instalments, one per term, each carrying term. A plan still overrides this

New Tuition packages replace fee plans

A package is "so many classes for so much, on any subjects": amount and classes_included, with per_class_amount derived. A student is put on a package for a term; their usage (classes used and remaining) is counted from that term's first day. billing_mode decides when the money is asked for: PER_CLASS bills the classes attended each period at the per-class rate; PACKAGE bills the whole amount on the first invoice of the term and thereafter only classes beyond the allowance.

Removed: /admin/tuition/fee-plans (all four verbs) and fee_plan_id on TuitionEnrollmentCreate, TuitionEnrollmentUpdate, TuitionEnrollmentOut and StudentSubjectAdd. The default_session_fee setting is gone from PUT /admin/tuition/settings/TUITION. A package's optional max_subjects makes POST …/students/{id}/subjects answer 400 once the student is at the cap.

Changed The tuition fee breakdown and invoice

TuitionFeeBreakdownOut (GET /tuition/students/fees/me, GET /admin/tuition/students/{id}/fee-breakdown, GET /parent/tuition/children/{id}) and InvoiceOut now carry term, term_name, package_id, package_name, assignment_id, billing_mode, classes_included, classes_billed, classes_used_to_date and classes_remaining at the top level. line_items holds one line, the package, and inside it subjects[] with each subject's classes_counted and session counts. Render the page as: package header with usage → one amount line (classes_billed × unit_amount, or package_amount + overage_amount under PACKAGE billing, with note / already_billed_on when the flat charge was raised earlier in the term) → the subjects table → discount, tax, convenience, total, exactly as before. The currency switcher is unchanged.

The lines CSV export is one row per subject with the package columns repeated; GET /admin/tuition/invoices/{id}/detail nests the sessions under each subject as well as on the line.

PaymentIntentOut now carries requested_method, program, invoice_number and reference ("PAY-<id>"). Render the result by status: checkout_url set → send the payer there; CREATED with a null URL → show detail and the reference; SUCCEEDED → paid. A draft, cancelled or settled invoice, or an amount over the outstanding balance, is a 400 with the reason. Nobody else's invoice is a 404.

The tuition InvoiceOut on the student and parent routes now carries amount_outstanding, gateway_enabled and gateway_provider, so the tuition checkout reads them exactly as the school's does. A provider callback on a tuition intent credits the tuition invoice.

19. Database backend — nothing changes for the frontend

New The backend can now serve the same API from Azure SQL instead of Firestore (DATABASE_BACKEND=azuresql). No endpoint, shape or id format changes. The one visible difference is that the Firestore free tier's daily read quota no longer applies, so the 503 database_quota_exhausted response disappears on that backend. GET /health/database reports which backend a deployment is on.

20. Admission fee once, tuition by term

Changed UserProfileFields and UserOut gain admission_year_id: the year the student first joined, set on creation and left alone by promotion. A fee head marked is_admission_charge is billed in that year only, so returning students never see it again. Each school InstalmentOut now carries components[] ({name, amount}): recurring fees split across the terms by the plan, and each one-time charge as its own instalment listed first, with term: null. A new admission's schedule reads Admission Fee 10,000 · Term 1 15,000 · Term 2 15,000; a returning student's has only the two terms. The user form offers "Admitted in year" next to the session year for students who joined before fees were on the system.

21. Collecting fees at the counter, and term-aware plans

New POST /admin/finance/students/{student_id}/collect takes a payment against a student: body is a PaymentRecord plus optional academic_year_id. The year's invoice is built and issued if the student has none, then the payment is recorded; the response is the updated FeeInvoiceOut. 400 when no structure applies or the amount exceeds what is owed. InstalmentLine gains term (TERM_1 / TERM_2) as an alternative to a due date or day count, and InstalmentOut carries term. Every school year now has a default "Two terms" plan, so the Instalment plans list is never empty for a year with fees.

22. Fee reports — the roll, the dues, the collections

Three read-only reports under /admin/finance/reports/, all admin-only and all taking program (default LMS). They are computed on request from the invoices and the roster and never stored, so a figure here is never a different figure from the Invoices tab; each response's summary is built from exactly the rows returned, so a filter changes the totals with the list. The admin Fees & invoices page shows them under a Reports tab with a class filter, a status filter on the roll, a period and method filter on collections, and a CSV button on each.

New GET /admin/finance/reports/students — every student assigned to the year, unbilled ones included. Query: academic_year_id (defaults to the current year), class_id, status, as_of. Each row carries status (NOT_BILLED / DRAFT / ISSUED / PARTIALLY_PAID / PAID / OVERDUE, the last one derived: an unsettled invoice with an instalment past due), invoice_id and invoice_number when there is one, total_amount, amount_paid, amount_outstanding, amount_overdue, expected_total (only for unbilled students: what the current rules would charge them), amount_due (the figure to chase either way), next_due (label, term, due_date, amount, is_overdue, days_overdue, or null), last_payment_at / last_payment_amount, an ageing object and the instalments with what each has paid. The status filter also accepts DUE, meaning anything owed. summary counts students by status and totals total_billed, total_collected, total_outstanding, total_overdue, expected_unbilled and total_due.

New GET /admin/finance/reports/dues — the same rows restricted to whoever owes, largest overdue balance first. ageing on each row and on the summary splits the balance into not_due, d0_30, d31_60, d61_90 and over_90 days past due, aged from each instalment's own due date; students not billed yet sit under not_due at their expected total.

New GET /admin/finance/reports/collections — every payment received between from_date and to_date (both required, inclusive), newest first, across every year unless academic_year_id is given; optional class_id and method. Rows carry paid_at, amount, currency, method, reference, note, instalment_label, the invoice and student identifiers, class_name and recorded_by_name. summary gives count, total, by_method, by_day and by_class.

Changed Every payment is now split by fee head, by replaying the invoice's own allocation (a payment naming an instalment goes to it, the rest cascade oldest-first, and each instalment's amount is shared across its components). A row carries heads ([{name, fee_head_id, is_admission_charge, amount}], admission first), admission_fee_amount, and instalments_settled, the labels a general payment actually cleared, to show in place of "oldest first". The summary adds admission_fees, other_fees, by_head ([{name, fee_head_id, is_admission_charge, count, total}]) and, when the new head_id query keeps only payments that settled one head, head with that head's own count and total. The CSV gains one column per fee head after the amount. The Reports tab shows "Admission fees" and "Tuition & other fees" cards, a fee filter, and the split on every row.

New GET /admin/finance/reports/export — the same three as CSV, view=students|dues|collections plus the filters above. The body is UTF-8 with a BOM and Content-Disposition names the file, so the frontend saves it exactly as the tuition billing export does. 400 when the view is unknown or a collections export lacks its dates.

New Opening-balance receipts. The students already on the roll paid their admission fee before this system existed, and an invoice cannot hold that (one invoice per student per year: a "paid admission" invoice for 2025-26 would be the year's bill). So money with no invoice is a receipt: POST /admin/finance/receipts with student_id, fee_head_id, amount, paid_at, method, optional reference, note and academic_year_id (defaults to the student's admission year); GET /admin/finance/receipts lists them (student_id, academic_year_id, fee_head_id filters) and DELETE /admin/finance/receipts/{id} erases one. Collections rows now carry source (INVOICE or OPENING_BALANCE) and receipt_id; a receipt row has no invoice_id, its heads is the one head, and it counts in admission_fees like any other. The Reports tab has a "Record past payment" button for one-offs; the bulk backfill for existing students is a backend script. A receipt never changes what a student owes.

One caveat for anyone timing this: the first request after the API restarts fills the document cache from the database and can take several seconds. Later requests take well under a second, and any payment or invoice change invalidates the reports along with the invoices in the frontend's query cache.

Questions on any shape here: the live schema at /api/v1/openapi.json is authoritative, and every endpoint carries a docstring explaining why it behaves as it does.
